# ATTa v121.2: every app is its own isolated, parallel, revision-bound job

v121.2 builds on v121.1 and carries out the parallel-isolated-testing handoff. It works inside the existing
architecture. deployd, ADM, the six-stage watcher, qualification, the repair and lifecycle code, Stage-6
evidence and the Coolify handoff all stay authoritative. Nothing here is a sidecar.

## What was wrong in v121.1 (reproduced before fixing)

| # | Defect | Effect | Proof |
|---|---|---|---|
| 1 | `deployment_revision()` looked for `release.json` only under `APP_BUILDER_ROOT`. Inside the Coolify container nothing puts it there, so it returned `unknown`, and `revision_stable("unknown", "unknown")` is False. | **Every app would have been marked UNVERIFIED.** No app could ever reach Coolify. | Run against the v121.1 code with a Coolify layout: `revision = unknown, stable = False` |
| 2 | The job identity (`_run_id`, `_deployment_revision`, `_attempt`) was written into `state/apps/<app>.json`. | The `--loop` watcher reads that file, so its later checks were stamped with a finished job's run ID and revision. That is cross-attached evidence. | Test `test_identity_travels_in_memory_never_in_the_target_file` |
| 3 | Stage-6 evidence was written to `evidence/<app>/`, one folder per app. | Each new check (a rerun, the loop watcher, the next build) overwrote the pictures that an older result still pointed at. That is evidence from another run or revision. | Test `test_each_check_has_its_own_folder_with_its_identity` |
| 4 | The fleet used `pool.map(...)`, and `_synth()` needs the app's folder. | Any exception outside `qualify_app` aborted the whole fleet and lost every result. | 5 | When the revision changed, the app was only marked UNVERIFIED. | The spec requires: invalidate and **rerun**. | Test `test_revision_change_mid_check_is_discarded_and_rechecked` |
| 6 | Nothing limited how long one job could run. | A hung job blocked the fleet forever, so there was no aggregate. | Test `test_a_hung_app_is_timeout_and_the_fleet_still_reports` |
| 7 | Two different names with the same `safe_id` (for example `My_App` and `my-app`) were both run. | They shared a workspace, containers, ports, result file and evidence. | Test `test_colliding_identities_are_reported_not_merged` |
| 8 | There was no aggregate report: no totals, no failures by class, no concurrency record, no timeouts or resource events. ## What v121.2 does

**Job identity.** Each app's job has its own:
- run ID
- fleet run ID
- attempt number
- correlation ID (new for every attempt)
- deployment revision: the ADM release plus a content hash of the running code, never `unknown` while the code can be read
- app revision: source commit, intake record, and the skin/port files

This identity is recorded on the result, on every `evidence.jsonl` row and in every Stage-6 `browser.json`. It is held in a per-thread job context and only ever attached to that same app's records.

**Isolation.** The runner already gave each app its own:
- workspace (`work/<app>`)
- Compose project and network (`atta-<app>`)
- host ports, handed out under a lock
- data folder
- skin-proxy process
- browser process (a fresh Chromium for every check, with no shared profile)

v121.2 adds:
- one evidence folder per check: `evidence/<app>/<run>-a<attempt>/`, or `watch-…` for loop checks. Folders are never overwritten and are pruned oldest-first, keeping `APP_BUILDER_EVIDENCE_KEEP` (default 20).
- identity kept out of shared files.
- identity-collision detection.

**Concurrency.** All apps are still queued at once by default (`APP_BUILDER_RUN_PARALLEL=0`). The memory and disk gates remain as safeguards. The report records:
- the mode (`parallel`, `capped`, `sequential` or `single`) and the reason
- the cap
- the **peak number of apps actually running at once**
- each wait for machine room
- each disk prune
- each app re-checked in the sequential second pass

`APP_BUILDER_RUN_PARALLEL=1` logs `WARNING: … ONE AT A TIME`.

**Failure containment.** Every exception becomes that app's own recorded result:
- `RUNNER_EXCEPTION`: inside the check.
- `WORKER_EXCEPTION`: anywhere else in the job, or thrown out of the worker.
- `WORKER_TIMEOUT`: the job outlived `APP_BUILDER_APP_HARD_TIMEOUT`, which defaults to `max(2 × APP_TIME_BUDGET, 7200)` seconds counted from when the job leaves the queue. The fleet stops waiting, stops the app's containers and carries on. If the job finishes later, its result goes to `results/late/` and never overwrites the recorded one.

The fallback builders work even when the app's folder or the watcher module is what broke.

**Final verification barrier, per app:**
1. Capture the deployment and app revisions.
2. Readiness and qualification (`qualify_app`: start, settle, six stages, Stage-6 evidence).
3. Capture both revisions again.
4. If both are unchanged, accept the result.
5. If either changed, record the attempt (with its evidence) under `verification.invalidated_attempts`, never on the result, and check the app again. This repeats `APP_BUILDER_REVISION_RERUNS` times (default 1). If the revision is still changing, the result is `UNVERIFIED`, stage 6 is set to FAIL with `DEPLOYMENT_CHANGED_DURING_CHECK`, and no old-revision evidence is kept on it.

**Fleet barrier.** At the end of the run, any QUALIFIED result checked against a revision that is no longer live is re-checked, then marked `UNVERIFIED` (`DEPLOYMENT_CHANGED_DURING_FLEET_RUN`) if it still doesn't match. The pipeline hands off only results that are `QUALIFIED` **and** were made on the revision live at hand-off time. Results kept from earlier checks, and pre-v121.2 results with no barrier, are not accepted.

**Outcome vocabulary** (`result.handoff_state`, exactly one per app):
- NOT_STARTED
- START_FAILED
- TIMEOUT
- INCONCLUSIVE
- FAILED
- QUALIFIED
- UNVERIFIED

**Observation ladder** (`result.levels`). Each level is recorded separately; a higher level is never inferred from a lower one:
- `tcp_reachable`
- `http_response`: from the contained probe, which runs right after start
- `healthy`: settled, and the watcher reached the app and the proxy
- `qualified`: all six stages passed
- `verified`: qualified, and the barrier held

**Aggregate report.** Written to `state/runner/RUN-REPORT.{json,md}` (the latest run) and `state/runner/runs/<fleet run id>/report.{json,md}` (kept). It contains:
- one row per app: state, levels, stage, code, run, attempt, revisions, evidence folder
- totals by state
- failures grouped by state, stage and code
- concurrency used
- timeouts
- every resource or timeout event
- whether the deployment revision stayed stable for the whole run

The build record carries a summary as `fleet_report`.

**Gateway.** Evidence links are `/evidence/<app>/<run>/<file>`. The old `/evidence/<app>/<file>` form serves only the flat files from before v121.2. It never falls through to a newer run.

**Kit.** Includes the tested shared fix from the deployment PR:
- `ensure_registry_mirror`: sets the Docker Hub mirror before the installer and before every build, with a Docker restart only when needed.
- `wait_for_coolify_api`
- `--domain` accepts a comma-separated list.
- Tests: `mirror.bats` and `deploy_domains.bats`.

## Validation (run here, 2026-09-29)

- Full Python suite: 142 passed, 4 skipped. v121.1 as received: 114 passed, 2 failed, 4 skipped.
- New suite `tests/test_v121_2_parallel_isolation.py`: 26 tests. They run the real runner, watcher, pipeline, gateway (as a process) and resilience code. Only the Docker host is stood in, with jobs that sleep, crash, hang or change the app mid-check.
- Mutation check: 14 of the fixes above were reverted one at a time, and a test failed every time.
- Image layout: the tree was laid out the way the Dockerfile's COPY and rm steps leave it, and a fleet was run from it. The revision was stable, the peak was 3 of 3, and the report was written.
- ADM `staging.check` accepts the bundle.
- Kit: bats 80/80, shellcheck clean.

Not validated here: a live fleet run on the server. That needs the operator's go-ahead, because ATTa is stopped by instruction.
