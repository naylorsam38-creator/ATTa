# v112 — every app in an upload is found, run, checked and evidenced (2026-09-25)

Built on the v111a-ADM bundle. Nothing in the worker pool, the six-stage gate, ADM, the rule
lifecycle or the heal chain was replaced. What changed, and what proved it.

## The bug
A zip laid out as `bundle/README.txt` + `bundle/apps/memos-main/` + `bundle/apps/homepage-main/`
went into the library as ONE app called "apps" (reproduced on the shipped v111a before any change).

## What was built
1. `04-deployment/app_discovery.py` (new). Walks the whole upload, any depth. A folder is one app when
   it has `.git`, a code marker, or when its code-carrying children are all role-named (client/server/
   backend/web/api...). Everything else is a container and is walked. Junk folders never count.
   Command line: `python3 app_discovery.py <unpacked folder>` prints the apps it would file.
2. `pipeline.py`: `ingest_upload` uses it. New build step `DISCOVERING`; the build record carries
   `apps_discovered` (name, where in the zip, how recognised). Each app is filed, catalogued and queued
   into the existing parallel pool on its own.
3. `system_watcher.py`: stage 6 keeps what the browser saw for every app, pass or fail:
   `state/runner/evidence/<app>/screenshot.png`, `page.html`, `browser.json` (page errors, console errors,
   failed requests). Attached to the stage-6 result and the build record. Off with
   `APP_BUILDER_CAPTURE_EVIDENCE=false`.
4. `gateway.py`: the build page shows "Apps found in the upload" and "What the browser saw" with links;
   `/evidence/<app>/<file>` serves the three files to logged-in users only.
5. `app_runner.py` — two failure classes found on the real run, fixed as rules for the class:
   - `app.host_rejected`: a web app that refuses the probe's Host header (Homepage
     `HOMEPAGE_ALLOWED_HOSTS`, Django `ALLOWED_HOSTS`, `TRUSTED_HOSTS`) answers 4xx JSON and names the
     variable in its own log. Before: reclassified as a "service" and given a FALSE PASS with no skin,
     hook or browser. Now: the variable is set to `*` and it starts again; only a 2xx/401 non-HTML
     answer may reclassify a web app.
   - `container.missing_path` + documented mounts: an image part gets an anonymous volume at every
     mount the app's own `docker run` example names (`-v x:/app/config`); a running app that logs
     `ENOENT` on a path gets one there too. Recipes now keep `volumes`.
   - The disk-room wait in `_start` is logged every tick and recorded on the attempt (it was silent and
     read as a hang).

## What proved it (real system, real Docker, real Chromium, real gateway upload — no mocks)
Seven uploads of the same zip holding two real apps from the registry, Memos and Homepage:
- discovered 2 apps every time (`homepage apps/homepage-main`, `memos apps/memos-main`)
- final runs: build QUALIFIED; both apps PASS all six stages; skin OK, hook OK, adapter dormant;
  checklist 2/2 complete, regressions none; evidence files written and served
- Homepage's two fixes were learned into its recipe; the following upload started it correctly on
  attempt 1 ("recipe that worked before env=['HOMEPAGE_ALLOWED_HOSTS']")
- Coolify hand-off: BLOCKED_NOT_CONFIGURED (no Coolify in the test box — expected)

## Not exercised by this run
The maintenance.py heal chain (script → adapter → LLM → human): both apps were repaired inside the
runner before the qualify layer failed, so the chain had nothing to do. It is unchanged from v111a.
