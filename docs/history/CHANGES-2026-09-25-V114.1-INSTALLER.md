# v114.1 — installer fixes (2026-09-25)

Built on v114. Only the installer (`bootstrap.sh`) and the files it uses changed; the pipeline, runner,
ADM's deploy steps and v114's hardening are as they were.

## What changed
1. **`.env` is read as data, never run.** `bootstrap.sh` used to `. .env`, so a line like
   `X=$(command)` ran as root. `envfile.py` (new) reads it line by line: `NAME=value` only, one optional
   pair of quotes, no `$`, backtick, backslash or control characters. A bad line stops the install and
   names the line number, never the value. Names this system doesn't use are reported and not exported.
   Only the three settings `accounts.py init` needs are passed to it. The services still get the whole
   file through systemd's `EnvironmentFile=`, which doesn't run shell either.
2. **Permissions on every run.** `.env`, `coolify_resources.json`, `TEST_ACCOUNTS.txt` and the JSON
   files in `state/` and `state/apps/` become `root:root 0600`, and those two folders `0700`, on every
   run, not only when first created. App data under `state/runner/work` is deliberately left alone:
   containers write there as their own users.
3. **Docker Compose pinned and verified.** The fallback download (used only when the package manager
   has no Compose) is now v5.5.1 over HTTPS only, with its SHA-256 checked before install
   (hashes cross-checked against the release's `.sha256` files and `checksums.txt`, and by hashing the
   downloads). Machine types are mapped explicitly (x86_64/amd64, aarch64/arm64); anything else is
   refused before any download. Updating Compose = editing three lines at the top of `bootstrap-lib.sh`.
4. **Services wait for Docker.** Pipeline and watcher: `Requires=docker.service`,
   `After=network-online.target docker.service`, and `ExecStartPre=wait-for-docker.sh`, which waits up
   to 90 s for `docker info` to answer. All three services restart after 5 s; 10 failed starts within
   5 minutes stop the loop (`systemctl status` shows it; `systemctl reset-failed` + start resumes).
5. **Clean code releases.** Each run copies the code into a new folder
   `/opt/app-builder-releases/<version>-<time>/` (regular files only: no symlinks, no caches), checks every
   `.py` compiles, and only then switches `/opt/app-builder` (now a symlink) with one atomic rename.
   Deleted files really disappear. The previous release is kept; after the health gate passes, older
   ones are pruned (newest 3 kept, plus live and previous). On a server laid out the old way, the old
   folder is moved to `legacy-<time>` and kept as the previous release.
   If the health gate fails on a run started **by hand**, the previous code is put back and restarted.
   Under ADM (`ATTA_ADM_ACTIVE=1`) nothing is undone by the installer: ADM's rollback stays in charge.

Unchanged on purpose: the IPv4 + IPv6 metadata block, and an existing `/etc/docker/daemon.json` is
never replaced (only created when missing).

## What proved it
`tests/test_v1141_installer.py`, 25 tests (45 with v114's), run as root here:
- 9 malicious `.env` lines (`$(...)`, backticks, `${}`, `export`, injected commands, bad names, stray
  quotes, backslashes) are refused and never run; the old `. .env` shown to run them
- wrong checksum, tampered download, unsupported machine types refused and nothing installed; the real
  pinned download from GitHub verified and run (`ATTA_TEST_NETWORK=1`)
- stale file gone after a redeploy; old layout migrated; broken code never goes live; symlinks not
  copied; restore + prune keep live and previous; ADM backup copies through the symlink
- permissions and ownership enforced again on a rerun; app data folders untouched
- Docker readiness: waits through two failures, gives up when Docker never answers
- unit files: ordering, readiness step, start limits; gateway doesn't depend on Docker

Also run for real (outside the tests): the deploy section of `bootstrap.sh` twice from the bundle and once
from an ADM-style backup of the live folder.

**Not proved here:** a full `bash run` under systemd on a real server. The first run on the AWS box is
also the first real test of the migration from a plain `/opt/app-builder` folder to the symlink.

## Still open
The pipeline runs as root and controls Docker. The long-term fix is moving untrusted build/run work to a
separate worker or VM behind a narrow job interface.
