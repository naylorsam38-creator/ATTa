# ATTa v121.1 — integrated resilience hardening

This release applies the resilience work **inside the existing ATTa architecture**. It is not a sidecar replacement and does not replace deployd, the six-stage watcher, qualification logic, repair flow, Stage-6 evidence, or lifecycle state.

## Integrated changes

### Probe containment
- HTTP probes now run through the resilience boundary.
- Malformed/non-HTTP responses, TLS/protocol mismatches, timeouts, connection errors, and unexpected probe exceptions are classified rather than allowed to crash the app runner.
- TCP reachability is retained as evidence but is never treated as application health.
- A successful HTTP response remains a probe observation, not an automatic `QUALIFIED`/`VERIFIED` verdict.

### Deployment revision boundary
- Every app qualification run records a run ID and the deployment revision captured before testing.
- Stage-6 browser evidence carries the run/revision/attempt identity when available.
- The deployment revision is checked again after qualification.
- If the deployment changes during the check, the result is marked `UNVERIFIED` and the qualification must be rerun against the current revision.
- Evidence from an older deployment revision cannot satisfy the current verification barrier.

### Parallel execution
- Existing v121 parallel execution remains in place: with `APP_BUILDER_RUN_PARALLEL=0`, all discovered apps are queued into the parallel pool.
- Existing memory/disk/download gates remain safeguards; they do not turn the run into sequential app testing.
- Per-app exceptions remain contained so one app does not abort the fleet run.

## Preservation

The original v121 architecture remains authoritative. These changes are integrated into the existing runner/watcher boundary rather than adding a second deployment or verification system.
