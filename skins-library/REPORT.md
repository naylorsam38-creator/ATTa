## The one real gap: found, not guessed around

The command asked for skins to be "referenced the way skins are already
referenced." The real, live pipeline (`choice.json` -> `build.py` stage 6 ->
`skin.json`, confirmed by reading `build.py`'s `stage1_assemble()` and every
built app's own `skin.json`) has exactly one visual field that reaches a
built app's actual rendered output with **zero builder-side code changes**:
`branding.color`, a single accent hex baked verbatim into the generated CSS.
`skin_id`/`skin_version` are carried through as inert labels; `arrangement`
only ever records slot *positions*, never style. There is no existing code
path anywhere in this repository that resolves a `skin_id` into a stylesheet
-- every app's CSS is a literal string baked in at generation time by its
own hand-written generator function in `verification/app_defs.py` /
`verification/gen_common.py`.

That means a *full* skin -- typography, spacing, radius, shadows, states,
the actual "read shadcn/ui, rebuild the whole system" ask -- cannot be wired
into a real running app today through configuration alone. Doing so for
real (not a sandbox trick) requires the generator itself to read a skin file
and bake its complete CSS instead of a single hardcoded block. That is a
change to `gen_common.py`/`build.py` -- explicitly out of this command's
scope ("no app logic, no builder behaviour"), and squarely the kind of
change the parallel `BUILDER_COMMAND.md` track owns.

**What this means concretely, reported rather than papered over:**
- All 172 full skins are real, complete, professionally-built design
  systems, verified rendering correctly and preserving every app's
  functionality (`full_skin`: 172/172 PASS above).
- 168 of 172 are *also* immediately production-adoptable through the
  existing mechanism today, using their primary accent color as
  `branding.color` (see each skin's `*.choice_fragment.json` -- copy it
  into an app's `choice.json` and rebuild; no code changes needed).
- `todo_list`'s 4 skins fail that one dimension for a real, verified reason:
  its own generated `app.py` never references `branding.color` anywhere in
  its CSS (confirmed by string search -- zero occurrences), so there is
  nothing to substitute. This is a fact about that one app's own generator,
  not a defect in the skins.
- The full typographic/spacing/shadow richness of every skin is proven to
  render correctly (Track A), but is **not yet adoptable in production**
  without a generator change outside this command's authority. Flagging
  this rather than either (a) silently shipping 4 recolors and calling it
  "shadcn/ui-quality," or (b) refusing to build anything.

## Numbering

No new permanent (registry-governed) numbers were needed or assigned.
`skin_id` is not part of the CAP-/APP-/SCR-/BTN- numbering system --
confirmed by reading `build.py`'s `stage1_assemble()`: `skin_id` is copied
verbatim from `choice.json` with no allocation function and no registry
check, unlike `allocate_app_id()` for APP numbers. New IDs (`skin-002`
through `skin-005`) continue the one existing precedent (`skin-001`)
sequentially. Nothing here touched `CANONICAL_SPEC.md`'s numbered-record
freeze.
