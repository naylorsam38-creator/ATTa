# DECISIONS — architectural decision record

Each decision states what was chosen and why. Stage 01 decisions are D-001 … D-022. Later stages append.

| ID | Decision | Reason |
|---|---|---|
| D-001 | **Additive monorepo.** The new platform (`backend/`, `apps/`, `packages/`, `capabilities/`, …) is added next to the existing ATTa v121.5 app builder (`01-specs/` … `05-coolify/`, `docs/`, `run`, `tests/test_*.py`), which is left byte-for-byte unchanged. | "Do not delete, replace or downgrade existing working functionality." The app builder becomes the engine behind CAP-18 (application creation) in Stage 11 instead of being rewritten. S01-T16 enforces it. |
| D-002 | `docs/` is kept as the legacy ATTa operations documentation; `documentation/` holds platform documentation. | `docs/` is referenced by the legacy README and runbooks; renaming would break them. `documentation/README.md` links both. |
| D-003 | Extra backend packages beyond the mandated list: `backend/contracts`, `backend/settings`, `backend/service_manager`, `backend/database`. The build controller lives in `backend/verification`. | Each holds one concept that the mandated directories consume (contracts are shared by all; the service manager is not an AI orchestration concern). The build controller is verification tooling, so it sits with evidence capture instead of a new top-level directory. No concept is implemented twice. |
| D-004 | **Python 3.12–3.13**, FastAPI + Pydantic v2, Uvicorn. | Async-capable, typed request validation, OpenAPI for free, mature ecosystem for LiteLLM/LangGraph/Temporal SDKs. 3.13 is the build environment's interpreter; 3.12 is the minimum the AI libraries support well. |
| D-005 | **Dependency locking:** `pyproject.toml` ranges + `uv.lock` (exact), exported to `configuration/locks/*.lock.txt` with `--require-hashes` so plain `pip` (Windows without uv) installs exactly the same artefacts. Node: `package-lock.json` (root workspaces) and `apps/mobile/package-lock.json`. | Reproducible, tamper-evident installs on every OS. |
| D-006 | **Supply-chain cool-down:** `[tool.uv] exclude-newer = 2026-11-10` and npm versions chosen ≥ 2 weeks old at lock time; LiteLLM 1.82.7/1.82.8 (compromised PyPI releases, March 2026) explicitly excluded. | Fresh releases are the window in which malicious publishes are caught. |
| D-007 | **AI stack selected and locked, not yet wired:** LiteLLM 1.108.4 (model gateway), LangGraph 1.2.20 (orchestration), temporalio 1.35.0 (durable workflows), pgvector 0.4.x (Python), installed with `INSTALL --with-ai`. | Stage 01 is infrastructure; wiring them now would be untested placeholder code. Locking now guarantees compatibility (one resolver pass over the whole stack). |
| D-008 | Locked core versions: fastapi 0.162.2, starlette 1.10.0, pydantic 2.14.3, uvicorn 0.54.0, psycopg 3.3.8, redis-py 7.4.1, jsonschema 4.x, boto3, psutil 7; Node: Next.js 16.4.6, React 19.3.1, TypeScript 5.9.3, Vitest 4.1.12, Electron 45.2.3, React Native 0.88.1, @playwright/test 1.63.0 / playwright (Python) 1.63.0. | Current stable lines inside the cool-down. TypeScript 5.9 rather than 7.x (native port) for tool compatibility. Playwright 1.63.0 matches the Chromium build already provisioned (no browser download). React 19.3.1 satisfies RN 0.88's `react ^19.3.0` peer and Next 16. |
| D-009 | **Identifiers:** `<prefix>_<ULID>` (e.g. `tsk_01M8…`). | Globally unique, time-sortable, type-tagged, URL-safe; prefixes catch mixing ids of different kinds. |
| D-010 | **API:** every route under `/v1`; every error is `{"error": {code, message, correlation_id, details}}`; `X-Correlation-ID` accepted only if well-formed, otherwise minted; `Idempotency-Key` scoped per principal (in-memory or Redis store). | Stable versioned contract for three clients; uniform error handling; log-injection-safe correlation. |
| D-011 | **Readiness is measured, not asserted:** `/v1/health/ready` probes every non-disabled dependency concurrently on each call (real TCP/HTTP/SQL/PING/HeadBucket). 503 when any *essential* dependency is unhealthy; `degraded` when only optional ones are. Liveness is process-only. | Requirement: readiness must reflect actual dependency health; an essential failure must never be masked. |
| D-012 | Essential services (Stage 01): PostgreSQL (with pgvector installed), Redis, API. Optional: S3 object storage, Temporal, model endpoints. Production makes object storage essential. | Nothing in Stage 01 stores objects or runs workflows yet; marking them essential would make a correct system "not ready" for no functional reason. |
| D-013 | **Service manager** = Python process supervising children (`subprocess` + `psutil`): topological start order, per-service startup timeout, health monitor, bounded restarts (count within a sliding window, exponential backoff), reverse-order shutdown with SIGTERM→SIGKILL, state in `runtime/state/manager.json`, stop via a stop-request file (works on Windows, where signals are limited). | One supervisor for Windows and Linux without systemd/NSSM; START.bat and start.sh both just invoke it. |
| D-014 | PostgreSQL runs **external** by default (local install or Docker); Redis is **managed** (spawned) on port 6380. | pgvector is not a trusted extension, so creating it needs a superuser — a one-time bootstrap (`database/bootstrap.sql`) the service manager must not perform. Redis is light and safe to supervise; 6380 avoids colliding with a system Redis. On Windows Redis runs via Docker/Memurai and is switched to external by one setting. |
| D-015 | A managed service whose port already answers before start is a **startup failure**, not success. | Prevents false readiness from a foreign or stale process. |
| D-016 | **Single capability registry**: manifests are `capabilities/*/capability.yaml` (JSON-Schema-validated, schema shared with the TypeScript SDK); handlers are `module:function` resolved only inside the capability directory (symlink escape refused); all copies of a duplicated id are rejected; dependencies (capabilities, services, Python modules) are resolved topologically; health checks run with a timeout; only `available` capabilities execute, and only after the policy engine allows it. | Requirement §5. Rejecting *all* duplicates (not "first wins") means an attacker-planted manifest can never shadow a legitimate one. |
| D-017 | **Security, Stage 01:** a central `PolicyEngine` allows only `health.live`, `health.ready`, `system.version`; everything else is DENIED (even principals claiming `*` permissions, even with a bearer token — the Stage 01 authenticator returns ANONYMOUS for every request). `grant()` is refused for agents, capabilities, workers, anonymous and self-grants, and for everyone until Stage 02. API binds 127.0.0.1; a non-loopback bind is a configuration error unless explicitly allowed. PostgreSQL tables use FORCE ROW LEVEL SECURITY with no policies (default deny). | Requirement §11. |
| D-018 | **Build controller**: task/stage definitions + acceptance tests are protected files sealed by SHA-256 (HMAC with an operator key kept outside the repo when configured); results only come from executed commands and are appended to a SHA-256 hash-chained ledger with evidence-file digests; there is no approve/override command; stage N+1 refuses to run until stage N's gate passed; changed files must match task permitted paths and never stage protected paths. | Requirement §8. Limitation recorded in BLOCKERS B-009: an actor with unrestricted write access to the repository *and* the operator key could still forge records; tamper-evidence plus git history plus operator signing is the achievable guarantee. |
| D-019 | **Recovery checkpoints**: the Stage 01 gate records the baseline checkpoint, then every fourth stage (S04, S08, S12, S16, S20). A checkpoint names a clean commit, the migrations it knows and the sealed-criteria digest. RECOVERY is non-destructive: it stops services, stashes current work (including untracked files) and switches to a new `recovery/…` branch at the checkpoint; it refuses checkpoints older than the database's applied migrations. | Requirement §8/§9: "restore the last verified compatible checkpoint". |
| D-020 | **Clients:** npm workspaces for `packages/*`, `apps/web`, `apps/desktop`; `apps/mobile` has its own lockfile (Metro and hoisted workspaces conflict). `.npmrc legacy-peer-deps=true` because npm 10.9's resolver crashes (`edgesOut` of null) on Vitest's optional peers; peers are declared explicitly instead. Electron's binary download is skipped unless `--with-desktop`. | Working, reproducible installs with the toolchain that exists today. |
| D-021 | **Web** = Next.js App Router server component calling the API server-side through the shared `@atta/api_client`; **desktop** = Electron shell over the web UI (contextIsolation, sandbox, no Node in renderer, single-origin navigation, all permission requests denied); **mobile** = React Native app over the same client and design tokens. | One UI codebase for web+desktop; shared typed client and tokens for all three. |
| D-022 | **Infrastructure:** Docker Compose for PostgreSQL+pgvector, Redis, optional MinIO/Temporal/API, every port bound to 127.0.0.1; Terraform module for the same single-host topology via the Docker provider. No cloud resources are defined. Model files live wherever `ATTA_MODEL_PATHS` / `models.storage_paths` point (D:\, USB drives); nothing is downloaded (`allow_model_downloads: false`), remote paid endpoints are not even probed unless `allow_paid_infrastructure: true`. | "Do not download large models or start paid infrastructure without explicit authorisation"; "do not require model files on the Windows system drive". |
