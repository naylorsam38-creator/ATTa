# DECISIONS — architectural decision record

Each decision states what was chosen and why. Stage 01 decisions are D-001 … D-022. Later stages append.

| ID | Decision | Reason |
|---|---|---|
| D-001 | **Additive monorepo.** The new platform (`backend/`, `apps/`, `packages/`, `capabilities/`, …) is added next to the existing ATTa v121.5 app builder (`01-specs/` … `05-coolify/`, `docs/`, `run`, `tests/test_*.py`), which is left byte-for-byte unchanged. | "Do not delete, replace or downgrade existing working functionality." The app builder becomes the engine behind CAP-18 (application creation) in Stage 11 instead of being rewritten. S01-T16 enforces it. |
| D-002 | `docs/` is kept as the legacy ATTa operations documentation; `documentation/` holds platform documentation. | `docs/` is referenced by the legacy README and runbooks; renaming would break them. `documentation/README.md` links both. |
| D-003 | Extra backend packages beyond the mandated list: `backend/contracts`, `backend/settings`, `backend/service_manager`, `backend/database`. The build controller lives in `backend/verification`. | Each holds one concept that the mandated directories consume (contracts are shared by all; the service manager is not an AI orchestration concern). The build controller is verification tooling, so it sits with evidence capture instead of a new top-level directory. No concept is implemented twice. |
| D-004 | **Python 3.12–3.13**, FastAPI + Pydantic v2, Uvicorn. | Async-capable, typed request validation, OpenAPI for free, mature ecosystem for LiteLLM/LangGraph/Temporal SDKs. 3.13 is the build environment's interpreter; 3.12 is the minimum the AI libraries support well. |
| D-005 | **Dependency locking:** `pyproject.toml` ranges + `uv.lock` (exact), exported to `configuration/locks/*.lock.txt` with `--require-hashes` so plain `pip` (Windows without uv) installs exactly the same artefacts. Node: `package-lock.json` (root workspaces) and `apps/mobile/package-lock.json`. | Reproducible, tamper-evident installs on every OS. |
| D-006 | **Supply-chain cool-down:** `[tool.uv] exclude-newer = 2026-11-10` and npm versions chosen ≥ 2 weeks old at lock time; LiteLLM 1.82.7/1.82.8 (compromised PyPI releases, March 2026) explicitly excluded. | Fresh releases are the window in which malicious publishes are caught. |
| D-007 | **AI stack selected and locked, not yet wired:** LiteLLM 1.108.4 (model gateway), LangGraph 1.2.20 (orchestration), temporalio 1.35.0 (durable workflows), pgvector 0.4.x (Python), installed with `INSTALL --with-ai`. | Stage 01 is infrastructure; wiring them now would be untested placeholder code. Locking now guarantees compatibility (one resolver pass over the whole stack). |
| D-008 | Locked core versions: fastapi 0.162.2, starlette 1.10.0, pydantic 2.14.3, uvicorn 0.54.0, psycopg 3.3.8, redis-py 7.4.1, jsonschema 4.x, boto3, psutil 7; Node: Next.js 16.4.6, React 19.3.1, TypeScript 5.9.3, Vitest 4.1.12, Electron 45.2.3, React Native 0.88.1, @playwright/test 1.63.0 / playwright (Python) 1.63.0. | Current stable lines inside the cool-down. TypeScript 5.9 rather than 7.x (native port) for tool compatibility. Playwright 1.63.0 matches the Chromium build already provisioned (no browser download). React 19.3.1 satisfies RN 0.88's `react ^19.3.0` peer and Next 16. |
| D-009 | **Identifiers:** `<prefix>_<ULID>` (e.g. `tsk_01M8…`). | Globally unique, time-sortable, type-tagged, URL-safe; prefixes catch mixing ids of different kinds. |
| D-010 | **API:** every route under `/v1`; every error is `{"error": {code, message, correlation_id, details}}`; `X-Correlation-ID` accepted only if well-formed, otherwise minted; `Idempotency-Key` scoped per principal (in-memory or Redis store). | Stable versioned contract for three clients; uniform error handling; log-injection-safe correlation. |
| D-011 | **Readiness is measured, not asserted:** `/v1/health/ready` probes every non-disabled dependency concurrently on each call (real TCP/HTTP/SQL/PING/HeadBucket). 503 when any *essential* dependency is unhealthy; `degraded` when only optional ones are. Liveness is process-only. | Requirement: readiness must reflect actual dependency health; an essential failure must never be masked. |
| D-012 | Essential services (Stage 01): PostgreSQL (with pgvector installed), Redis, API. Optional: S3 object storage, Temporal, model endpoints. Production makes object storage essential. | Nothing in Stage 01 stores objects or runs workflows yet; marking them essential would make a correct system "not ready" for no functional reason. |
| D-013 | **Service manager** = Python process supervising children (`subprocess` + `psutil`): topological start order, per-service startup timeout, health monitor, bounded restarts (count within a sliding window, exponential backoff), reverse-order shutdown with SIGTERM→SIGKILL, state in `runtime/state/manager.json`, stop via a stop-request file (works on Windows, where signals are limited). | One supervisor for Windows and Linux without systemd/NSSM; START.bat and start.sh both just invoke it. |
| D-014 | PostgreSQL runs **external** by default (local install or Docker); Redis is **managed** (spawned) on port 6380. | pgvector is not a trusted extension, so creating it needs a superuser — a one-time bootstrap (`database/bootstrap.sql`) the service manager must not perform. Redis is light and safe to supervise; 6380 avoids colliding with a system Redis. On Windows Redis runs via Docker/Memurai and is switched to external by one setting. |
| D-015 | A managed service whose port already answers before start is a **startup failure**, not success. | Prevents false readiness from a foreign or stale process. |
| D-016 | **Single capability registry**: manifests are `capabilities/*/capability.yaml` (JSON-Schema-validated, schema shared with the TypeScript SDK); handlers are `module:function` resolved only inside the capability directory (symlink escape refused); all copies of a duplicated id are rejected; dependencies (capabilities, services, Python modules) are resolved topologically; health checks run with a timeout; only `available` capabilities execute, and only after the policy engine allows it. | Requirement §5. Rejecting *all* duplicates (not "first wins") means an attacker-planted manifest can never shadow a legitimate one. |
| D-017 | **Security, Stage 01:** a central `PolicyEngine` allows only `health.live`, `health.ready`, `system.version`; everything else is DENIED (even principals claiming `*` permissions, even with a bearer token — the Stage 01 authenticator returns ANONYMOUS for every request). `grant()` is refused for agents, capabilities, workers, anonymous and self-grants, and for everyone until Stage 02. API binds 127.0.0.1; a non-loopback bind is a configuration error unless explicitly allowed. PostgreSQL tables use FORCE ROW LEVEL SECURITY with no policies (default deny). | Requirement §11. |
| D-018 | **Build controller**: task/stage definitions + acceptance tests are protected files sealed by SHA-256 (HMAC with an operator key kept outside the repo when configured); results only come from executed commands and are appended to a SHA-256 hash-chained ledger with evidence-file digests; there is no approve/override command; stage N+1 refuses to run until stage N's gate passed; changed files must match task permitted paths and never stage protected paths. | Requirement §8. Limitation recorded in BLOCKERS B-009: an actor with unrestricted write access to the repository *and* the operator key could still forge records; tamper-evidence plus git history plus operator signing is the achievable guarantee. |
| D-019 | **Recovery checkpoints**: the Stage 01 gate records the baseline checkpoint, then every fourth stage (S04, S08, S12, S16, S20). A checkpoint names a clean commit, the migrations it knows and the sealed-criteria digest. RECOVERY is non-destructive: it stops services, stashes current work (including untracked files) and switches to a new `recovery/…` branch at the checkpoint; it refuses checkpoints older than the database's applied migrations. | Requirement §8/§9: "restore the last verified compatible checkpoint". |
| D-020 | **Clients:** npm workspaces for `packages/*`, `apps/web`, `apps/desktop`; `apps/mobile` has its own lockfile (Metro and hoisted workspaces conflict). `.npmrc legacy-peer-deps=true` because npm 10.9's resolver crashes (`edgesOut` of null) on Vitest's optional peers; peers are declared explicitly instead. Electron's binary download is skipped unless `--with-desktop`. | Working, reproducible installs with the toolchain that exists today. |
| D-021 | **Web** = Next.js App Router server component calling the API server-side through the shared `@atta/api_client`; **desktop** = Electron shell over the web UI (contextIsolation, sandbox, no Node in renderer, single-origin navigation, all permission requests denied); **mobile** = React Native app over the same client and design tokens. | One UI codebase for web+desktop; shared typed client and tokens for all three. |
| D-022 | **Infrastructure:** Docker Compose for PostgreSQL+pgvector, Redis, optional MinIO/Temporal/API, every port bound to 127.0.0.1; Terraform module for the same single-host topology via the Docker provider. No cloud resources are defined. Model files live wherever `ATTA_MODEL_PATHS` / `models.storage_paths` point (D:\, USB drives); nothing is downloaded (`allow_model_downloads: false`), remote paid endpoints are not even probed unless `allow_paid_infrastructure: true`. | "Do not download large models or start paid infrastructure without explicit authorisation"; "do not require model files on the Windows system drive". |

## Stage 01A decisions

| ID | Decision | Reason |
|---|---|---|
| D-023 | **Stage order revised to S01 → S01A → S02 → … → S20** (user instruction). The Stage 02 corrections received just before Stage 01A were folded into Stage 01A where they are foundation work (§24 list) and recorded as Stage 02 items otherwise (BLOCKERS B-013). Account/session/MFA/RBAC code drafted for Stage 02 was removed from the tree before commit (archived outside the repository) so Stage 02 is not started. | "Implement Stage 01A before proceeding to Stage 02"; protected operations must stay default-DENY until Stage 02. |
| D-024 | **Two database credentials**: `atta` (schema owner, used only by `backend.database migrate`) and `atta_app` (runtime: table-level DML only, NOBYPASSRLS, no ownership). Readiness runs read-only (`default_transaction_read_only`) and fails if the runtime role can create objects, bypass RLS, touch migration records or owns any table. | Correction 7. Ownership is what permits `ALTER TABLE … DISABLE ROW LEVEL SECURITY`, so ownership is treated as over-privilege. |
| D-025 | **Supervised process execution** for every handler (probe, health, execute, verify, reconcile): API → `supervisor.py` (own session, Linux child subreaper, parent-death watch) → `child.py` (`python -I`, clean env, rlimits). The supervisor kills all descendants when the handler process exits, on timeout, cancel or controller death. | Correction 1. Waiting for the handler process (not pipe EOF) was required: a forked daemon holding the pipe otherwise delayed the kill long enough to act (found and fixed during development). |
| D-026 | **No capability code in the API process; operator-signed trust**. Discovery parses and schema-validates manifests only. Handler import/signature checks run in the isolated probe. A package runs only if the Ed25519-signed trust store lists its id, version, package digest, permissions and risk; the child re-hashes the exact bytes it executes and loads them from memory. | Correction 4; closes TOCTOU between check and load. |
| D-027 | **Topological evaluation with propagation** (dependencies, including their health, are final before dependents) and **live service health** (`HealthMonitor`: background probes + max-age on-demand refresh + change callbacks re-evaluating capabilities); `revalidate()` re-checks digest, trust, dependencies and services immediately before execution. | Corrections 2 and 3. |
| D-028 | **Precedence of availability problems**: invalid → duplicate → disabled → dependency_missing → untrusted / integrity_failed → probe-invalid → unhealthy. | Reports the most fundamental problem first; metadata-only checks need no code loading. |
| D-029 | **Five Stage 01 acceptance tests are superseded, not edited** (T06, T07, T08, T09, T13). They encode behaviour the corrections deliberately removed: untrusted packages being loaded, in-process handler objects, and direct `registry.execute`. S01A-T48 re-runs all Stage 01 tests, requires the other ten (plus T16 via T49) to pass, and proves the cause of each superseded failure by re-running them with trust satisfied by a test-only plugin. Each has stricter replacements (listed in the test). | "Do not weaken existing tests": the protected S01 files are unchanged (the S01A stage protects them); supersession is explicit, evidenced and stricter. |
| D-030 | **Runtime controller = `backend/orchestration`** (the single intelligence engine already reserved in Stage 01), extending the existing registry, policy engine, service manager and evidence ideas. The build controller (`backend/verification`) stays separate: engineering gates vs runtime control. | §2: no second engine, registry, orchestrator or startup path. |
| D-031 | **Permanent tool numbers `CCC.TTT`**, CCC = requirement-register capability number (CAP-40 → 040), assigned by the operator in `configuration/tool_numbers.yaml`, recorded in `control.tool_identifiers` (per catalogue namespace) whose trigger forbids reassignment, deletion and reactivation. A manifest without `tools` exposes one implicit tool `<id>:default` (compatibility). Any numbering inconsistency makes **no** tool allocatable. | §5 stability; fail closed. Test catalogues use their own namespace so test numbers never enter production. |
| D-032 | **Stage 01A policy rule**: user-facing protected operations remain DENY; `tool.execute` can be ALLOWED only for the attested runtime-controller principal, LOW risk, permissions granted to the controller in trusted config, and only when the request is bound to contract hash + tool id + canonical arguments hash + execution id. Medium+ risk and any approval requirement are DENIED until Stage 02. | §15 "until Stage 02 … protected operations must remain default-DENY; use controlled, harmless test handlers". |
| D-033 | **Principal attestation**: the controller signs its principal (HMAC, per-process key) and the policy engine trusts only registered attestors; a Principal object constructed elsewhere has no authority. Execute tickets for the runtime are signed by a gateway-private key bound once to the runtime. | A worker/agent/capability cannot mint authority or call the runtime directly (S01A-T11, T31). |
| D-034 | **Append-only controller records enforced in PostgreSQL** (triggers + grants) for objectives, contract versions, transitions, proposals, drift violations, verifications, evidence, checkpoints, recovery records; the task state machine is a DB trigger too. | Defence in depth: even SQL with the runtime credentials cannot rewrite history or skip states (S01A-T02, T11, T22, T33, T35, T39). |
| D-035 | **Focus-4** via a row lock on `control.objective_runtime` + `control.active_slots`; a batch's slots are released only after integration checks pass and a verified checkpoint is written. Repair tasks run inside their parent's slot and may use the parent's resource locks; other tasks may not. Resource locks are scoped per objective (`global:` resources are shared). | §10; concurrent controllers cannot exceed the limit (S01A-T14). |
| D-036 | **Bounded repair** creates a child task (new contract, parent's failed criteria only, repair tools only, failure evidence in its context) and re-verifies the ORIGINAL criteria after every repair; at most `max_repairs_per_task` (2), then FAILED with the unresolved criteria. | §18. |
| D-037 | **Operator authorisations** for objective approval/amendment, tool-pool changes and re-attempts after cancellation: Ed25519 signatures over (action, subject, payload hash, operator, expiry), public key in protected config. | Until Stage 02 provides authenticated humans, a key outside the repository is the only trustworthy authority. |
| D-038 | **Build seal signed with Ed25519** (`ATTA_BUILD_SIGNING_KEY_FILE`, public key `configuration/build/verifier_ed25519.pub`); from S01A the build controller refuses an unsigned seal and refuses to run without OS protection: protected files and the ledger owned by the verifier (root), not writable by the worker account (`atta-builder`), ancestors sticky (1775), signing key 0600 in a 0700 root directory (`scripts/protect_verifier.sh`). Protected criteria now include `backend/verification/**` and the trusted controller configuration. | Correction 8. In this build environment the implementing agent itself runs as root, so the boundary is demonstrated against `atta-builder` but does not constrain this session (BLOCKERS B-016). |

## Stage 12 sidecar decisions (connectors, MCP, skills, plugins) — NOT YET INTEGRATED

| ID | Decision | Reason |
|---|---|---|
| D-S12-01 | **An approved integration becomes an ordinary Stage 01A capability package** (generated `capability.yaml` + the integration's files + ATTa `_atta_*` bridge/verify/health modules) in `<install_root>/packages`, discovered by the ONE registry and numbered in the ONE catalogue. | "Do not create a second registry / execution engine"; reuses no-import discovery, isolated probe, digest re-verification, revalidate-before-execute. |
| D-S12-02 | **Composition via `attach()`**; Stage 01A changes are limited to two inert hook lists in the gateway (`guards`, `result_filters`) and an optional `extra_numbers` source in the catalogue. Guards can only refuse; filters can only keep or reject. | Smallest auditable change to the authoritative execution path; empty hooks = identical Stage 01A behaviour. |
| D-S12-03 | **`IntegrationTrustGate` is the registry's trust store for `integration.*` ids** and delegates everything else to the Stage 01A operator-signed store unchanged. It re-reads live state (enabled, trust class, isolation, connectivity, credentials, dependencies) on every registry evaluation, i.e. immediately before each execution. | Disable/offline/auth changes take effect at once, with existing AvailabilityState values. |
| D-S12-04 | **Operator Ed25519 authorisations** (same `OperatorAuthorization` as Stage 01A) for install, upgrade, enable and trust change, bound to `approval_binding()` (identity, digests, trust, permissions, every tool's schemas/side effect/risk, hosts, credentials, upgrade diff hash). Disable/remove need none. | Until Stage 02 a key outside the repository is the only trustworthy authority; binding to the diff makes silent permission expansion impossible. |
| D-S12-05 | **Permanent numbers for integration tools: CCC = type capability (021 connector, 022 MCP, 024 plugin, declared for custom providers), TTT 500–899 assigned automatically**, recorded append-only in `integrations.tool_numbers` and in `control.tool_identifiers`. Removal keeps the number reserved; reinstall/upgrade of the same tool reuses it. Operator-file numbers always win. | `configuration/tool_numbers.yaml` is protected/sealed; a disjoint band avoids collisions with operator numbering. |
| D-S12-06 | **Side-effect classes carry minimum risks** (READ_ONLY low … FINANCIAL/SECURITY_SENSITIVE critical) and connector operations carry minimum side effects; manifests may over-declare, never under-declare. The existing policy engine then denies medium+ until Stage 02 approvals. | Gives Stage 02 the metadata it needs without a competing approval engine. |
| D-S12-07 | **MCP: one stdlib wire implementation** used host-side (negotiation, discovery, health) and copied into packages for in-runtime `tools/call`; no client capabilities advertised; server `instructions` never forwarded; declared input schemas must match the server canonically; undeclared tools are ignored. | Single protocol code path; a server can never pull data/model output from ATTa or add tools after approval. |
| D-S12-08 | **Skills pin by contract**: `skill:<id>@<version> → content digest` inside the task contract's `input_checksums`; scripts run through `ScriptProposalSource` (labelled `atta-script`) and the normal controller loop. | Pin covered by the contract hash; no separate scripts engine. |
| D-S12-09 | **Integration descriptions are validated against instruction-like text**; outputs are not rejected for their wording but are redacted for secret patterns, flagged, audited and delivered only as `untrusted` context. | Tool descriptions enter the model's TRUSTED context section; outputs may legitimately quote such text. |
| D-S12-10 | **Separate configuration file `configuration/integrations.yaml`** (+ `ATTA_INTEGRATIONS__*`) instead of extending `backend/settings` | Stage 01B owns the configuration hierarchy; avoids merge conflicts. To be folded in at merge. |
| D-S12-11 | **Roadmap numbering mismatch recorded, not changed**: the protected roadmap names S12 "Skills, plugins, subscription, administration, data management" and places Connectors/MCP in S18; the parallel plan's Stage 12 = connectors/MCP/skills/plugins. No `configuration/build/stages/S12.yaml` was created or sealed; the sidecar is verified by `scripts/stage12_verify.py`. | Protected build-controller files may only change through the operator; reconciliation is a merge decision. |
| D-S12-12 | **Network destinations are a task-contract decision**: an integration declaring hosts executes only if all of them are in the contract's `permitted_network_destinations`. | Aligns with Stage 01B (host networking only for such contracts, empty namespace otherwise) and prevents an installed integration from widening a task's network reach. |
| D-S12-13 | **stdio MCP servers launch from the runtime's verified in-memory snapshot** (private temp dir) rather than the install directory. | Closes a TOCTOU window and works when Stage 01B drops workers to an account without read access to the install root. |
| D-S12-14 | **Adapters read other stages' interfaces duck-typed; most restrictive connectivity wins**, isolation is available only when the Stage 01B runtime REQUIRES it. | Same code on 01A, 01B, 11 and their merge; fail-closed; no imports of other workers' modules. |
| D-S12-15 | **Installer patches shared files hunk-by-hunk and documents by marked sections; conflicts stop everything; every write journalled; post-install verification or rollback.** | "Never overwrite working functionality" and "preserve other workers' additions" are enforced mechanically and tested on the real 01B and 11 trees. |
